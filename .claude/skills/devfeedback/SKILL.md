# DevFeedback の記録を読んで対応する

開発者はゲームを遊びながら、気づいたことや頼みたいことを**声で**話している。
その声（文字起こし）と、そのときの画面・操作・ログが1つのフォルダにまとまっている。これを読んで、手で打ったプロンプトと同じように扱う。

## 1. 記録フォルダを決める

- 開発者がフォルダ名やパスを指定していれば、それを使う
- 指定がなければ、プロジェクト直下の `DevFeedback/latest.txt` に書かれた名前のフォルダ（`DevFeedback/<名前>/`）
- 「さっきの2つ前」などと言われたら `DevFeedback/` 内のフォルダを日時順に並べて選ぶ

## 2. 文字起こしが終わっているか確認する

- `report.md` の「発話（文字起こし）」欄が「文字起こし中です」のままなら、`transcribe.log` を見る
  - 最後の行が「完了」になっていなければ、まだ処理中。数秒ずつ間を空けて、最大2分ほど待ってから読み直す
  - 「失敗しました」とあれば理由を開発者に伝え、再実行を提案する（必要なら自分で実行してよい）。コマンドは `python <transcribe.py のパス> DevFeedback/<名前>`
    - `report.md` に「実行するには: `...`」とコマンドが書かれていれば、それをそのまま使う
    - 無ければ `transcribe.py` を探す。場所はパッケージの入れ方で変わり、Git URL で入れた場合は `Library/PackageCache/com.devfeedback.recorder*/Tools~/transcribe.py`、`Packages/` に置いた場合は `Packages/com.devfeedback.recorder/Tools~/transcribe.py`。`Library/` は検索の対象から外れていることがあるので、見つからなければ `ls Library/PackageCache` で直接確かめる
    - 開発者が Unity を開いているなら、メニューの `Tools > DevFeedback > 最新の記録を文字起こし` でも再実行できる（最新の記録だけ）
- 音声が無い記録（マイクなし）なら、発話なしで進める

## 3. report.md を読む

`report.md` には、上から次のものがある。

1. **まず見るスクショ**: 自動で選ばれた、見るべきコマと理由。**画像はここに挙がったものだけを Read で見る**（全部は読まない）。足りないときだけ、「タイムライン」から気になる時刻の前後を追加で見る
2. **発話（文字起こし）**: 開発者がプレイしながら話した内容。**これが指示・要望・不具合報告の本体**
   - 「話し始めの画面」が、その発言をしたときに見ていた画面
   - 文字起こしには聞き間違いがある。ゲームの用語・画面の内容に合わせて読み替える（例: 固有名詞、カタカナ語）
   - 「ここ」「これ」は、そのときのスクショのカーソル・クリック位置を指していることが多い
3. **クリック・ドラッグ**: 番号つきのクリック一覧。スクショ上の黄色い点の番号と対応する
4. **エラー・警告**: スタックトレースつき。発言と時刻が近ければ、その不具合の手がかり
5. **タイムライン**: 全コマの時刻・シーン・timeScale・カーソル・クリック・ログ件数

スクショの印: **赤い輪** = 撮影した瞬間のカーソル（中が黄色ならボタンを押している最中）、**黄色い点と番号** = 直前の1秒間にクリックした位置、**黄色い線** = ドラッグの軌跡（終点に輪）。座標はすべて画面の左上が原点。

## 4. 理解した内容を開発者に返す

作業に入る前に、短くまとめて伝える。

- 発言ごと（または話題ごと）に「どの画面・どの操作について」「何を求めているか（不具合報告／要望／感想／独り言）」
- そこから導いた、やるべきことの一覧
- 聞き取りや意図があいまいなものは、推測を書いたうえで確認する
- 雑談や独り言（「テストテスト」など）は対応不要として扱ってよい

## 5. 対応する

- 指示がはっきりしているものから、コードを調べて対応する。発言の時刻の画面・ログを根拠にして原因を特定する
- 仕様の判断が要るもの、大きな変更になるものは、着手前に確認する
- 記録フォルダには開発者の声と画面が含まれる。外部のサービスには送らない
